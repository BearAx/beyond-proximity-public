\title{SemanticSplat: Graph-Pruned Semantic Search over \\ Captured 3D Gaussian Splatting Scenes}

\author{
Mahmoud Mousatat, Leo Vizan, Nikita Shankin, Telman Nuruzov, Alexandr Medvedev
}
\date{}

\maketitle

\begin{abstract}
3D Gaussian Splatting (3DGS) provides photorealistic rendering but no semantic structure for natural-language environment queries such as ``find a place where I can sit'' or ``where is the screen in the conference room?'' We present SemanticSplat, a rendering-first pipeline that builds a hierarchical semantic index from captured views and answers queries by traversing this index top-down, pruning irrelevant regions before leaf-level confirmation. To isolate the effect of hierarchy, we compare graph-pruned search against a flat baseline that scans the \emph{same} semantic items under an identical protocol. On five manually captured indoor and outdoor scenes (96 views, 1{,}046 semantic items) and 150 benchmark queries spanning six query types, graph traversal reduces average views checked by 71.4\% and input tokens by 65.1\% relative to flat search, while retrieval quality stays comparable: hit@1 is 0.792 (graph) vs.\ 0.768 (flat) and hit@3 is 0.904 vs.\ 0.928 on the 125 queries with verified view labels. A per-query-type analysis shows savings ranging from 53\% on multi-hop queries to 90\% on negative queries, revealing where hierarchy helps most. We report the setting honestly: manual reference labels rather than independent ground truth, and lexical stub matching rather than live provider-backed VLM evaluation.
\end{abstract}

\section{Introduction}
3D Gaussian Splatting~\cite{kerbl20233dgs} enables real-time, photorealistic novel-view synthesis, but the representation encodes only geometry and appearance. It does not know that a cluster of Gaussians is a ``chair,'' a ``reception desk,'' or a ``ballroom stage.'' For downstream tasks in robotics, AR/VR, and natural-language interaction, a scene must be \emph{queryable}: a user should be able to ask for an object, an attribute, or an affordance and receive the relevant viewpoint.

A natural approach is exhaustive (\emph{flat}) search: describe every captured view to a language model and let it pick the best match. This is simple but scales poorly---context length and cost grow linearly with the number of views, and unrelated rooms constantly compete for attention. Existing semantic-3D methods take two other routes. Language-field methods distill vision-language features into radiance fields or Gaussians~\cite{kerr2023lerf,langsplat2024}, which support point-wise relevance but lack explicit structure for context control. Explicit 3D scene-graph methods lift 2D detections into object graphs~\cite{gu2023conceptgraphs,bbq2024}, which can be fragile for open-vocabulary hierarchy construction.

SemanticSplat takes a rendering-first, hierarchy-first approach. We capture posed RGB views from a 3DGS scene, annotate them with structured records (objects, landmarks, room cues, and a short summary), organize them into a zone--region--object tree, and answer queries by traversing that tree top-down. Our central research question is deliberately narrow and testable: \emph{when a graph method and a flat method operate on identical semantic items, does hierarchical pruning reduce search cost without sacrificing useful retrieval quality?}

\paragraph{Contributions.}
\begin{itemize}
    \item A rendering-first semantic-map layer over captured 3DGS views, with MCP-backed infrastructure and query-flow logging.
    \item A controlled same-input benchmark comparing graph traversal to flat search over five captured scenes and 150 queries, measuring views checked, input tokens, and GT-aware hit@k.
    \item A per-scene and per-query-type analysis that quantifies \emph{where} hierarchy helps, plus an affordance-expansion layer for intent-style queries.
    \item Honest scoping: manual reference labels, stub evaluation mode, and baseline smokes reported without superiority claims.
\end{itemize}

\section{Related Work}
\paragraph{Language fields and 3DGS semantics.}
LERF~\cite{kerr2023lerf}, LangSplat~\cite{langsplat2024}, Semantic Gaussians~\cite{semanticgaussians2024}, and LEGS~\cite{legs2024} embed or distill vision-language features into radiance fields or Gaussians for open-vocabulary pointing and robot-scale mapping. Their native outputs are relevancy maps or semantic Gaussians rather than explicit traversal traces; they typically lack a zone--region--object hierarchy for context pruning.

\paragraph{Open-vocabulary 3D scene graphs.}
ConceptGraphs~\cite{gu2023conceptgraphs}, OpenScene~\cite{openscene2023}, ConceptFusion~\cite{conceptfusion2023}, and BBQ~\cite{bbq2024} build explicit graphs from lifted 2D detections, point clouds, or RGB-D association. These methods target object graphs, relational grounding, and planning; we instead evaluate whether a curated hierarchical index over captured views reduces same-input search cost for environment-understanding queries.

\paragraph{Hierarchical scene graphs and benchmarks.}
HOV-SG~\cite{hovsg2024} and Hydra~\cite{hydra2022} construct multi-level spatial graphs with stronger geometric priors for navigation and robotics. OpenLex3D~\cite{openlex3d2025} and ScanRefer~\cite{scanrefer2020} define tiered open-vocabulary and referring-expression benchmarks with 3D IoU and localization metrics on RGB-D scans. Our captured scenes lack independent object boxes or masks at that scale, so we report internal efficiency and GT-aware hit@k on verified view labels instead.

\paragraph{Token and context efficiency.}
Prompt compression~\cite{promptcompression2024}, AttentionRAG~\cite{attentionrag2025}, Provence~\cite{provence2025}, TeaRAG~\cite{tearag2026}, and S-Path-RAG~\cite{spathrag2026} study pruning retrieved context and graph-derived evidence for LLMs. Token count is not a standard 3D scene-understanding metric; we draw on this line to frame views checked and input tokens as internal graph-vs-flat efficiency measures, not as claims of superiority over RAG systems.

\paragraph{Positioning.}
We do not claim superiority over ConceptGraphs, LangSplat, or external graph builders. Our measured comparison is strictly internal: flat lexical search vs.\ graph traversal on identical scenes, semantic items, and query strings.

\section{Method}

\subsection{Capture and semantic index}
A user navigates a 3DGS scene in the browser and captures posed views (RGB, depth, and camera pose). Each view is annotated with a structured record listing visible objects, landmarks, room cues, and a short (10--15 word) natural-language summary. These records form the \emph{semantic index}: the atomic units that both the graph and flat methods search. Keeping the summaries short bounds the per-view token cost during traversal.

\subsection{Hierarchical tree}
Semantic items are organized into a three-level tree: \emph{zones} (e.g.\ lobby, ballroom), \emph{regions} within a zone, and \emph{object/view leaves}. Each internal node stores an aggregated summary of its subtree, so a traversal can decide whether to descend into or prune a branch by reading a compact node summary rather than every underlying view.

\subsection{Query traversal and flat baseline}
A query is decomposed into structured constraints (target object, attributes, spatial relations, query type). The tree is traversed top-down: at each node the model compares the query against the node summary and prunes irrelevant zones and regions before confirming at the leaf level. The \emph{flat} baseline removes the hierarchy entirely and scans the same semantic items exhaustively. Because both methods consume identical inputs, any difference in cost or quality is attributable to the pruning structure, not to different data.

\subsection{Affordance-aware expansion}
Intent queries are mapped to affordance categories before ranking---for example \emph{sittable} $\rightarrow$ chair, sofa, bench; \emph{exit} $\rightarrow$ door, stairs, sign. This deterministic expansion lets natural, goal-oriented phrasings resolve to concrete object candidates without a learned model.

\subsection{Evaluation protocol}
Graph and flat methods share scenes, semantic items, query strings, and benchmark labels. Efficiency metrics are views checked, input tokens, context size, and infrastructure elapsed time. Quality metrics (hit@1, hit@3) are computed only for queries with verified expected view IDs. We treat manual annotations as \emph{reference labels}, not independent ground truth, and all reported five-scene runs use lexical stub matching rather than live VLM API calls.

\section{Dataset and Benchmark}
The evaluation uses five captured scenes---three indoor (Conference Hall, Museum, Theater) and two outdoor (drone, street). Table~\ref{tab:dataset} summarizes their composition: 96 annotated views and 1{,}046 semantic items organized into deterministic trees. \section{Experiments}

\subsection{Main result: graph vs.\ flat}
Table~\ref{tab:five-scene} and Figure~\ref{fig:five-scene} report averages over all 150 queries. Graph traversal checks 5.39 views on average versus 19.2 for flat search (71.4\% fewer) and consumes 1{,}061.6 input tokens versus 3{,}104 (65.1\% fewer). Retrieval quality is preserved: graph hit@1 is slightly higher (0.792 vs.\ 0.768) while flat retains a small hit@3 edge (0.928 vs.\ 0.904), consistent with hierarchy trading a little recall breadth for large cost reductions. Figure~\ref{fig:cumulative} shows the effect accumulating across the benchmark: over 150 queries flat search consumes 466k input tokens versus 159k for graph traversal.

\subsection{Where does hierarchy help? Per-type analysis}
Aggregate numbers hide substantial variation. Figure~\ref{fig:by-type} and Table~\ref{tab:by-type} break token savings down by query type. Negative queries (``is there an X?'' when no X exists) benefit most: the tree prunes entire zones early, yielding 89.5\% savings and only 1.6 views checked. Simple-object, attribute, and functional queries land in a 63--67\% band. Multi-hop queries---which reference several entities across regions---show the smallest savings (53.0\%) and the highest graph view count (7.4), because they force the traversal to descend into multiple branches. This is the expected failure mode of hierarchy: it prunes best when a query localizes to one part of the tree.

\subsection{Per-scene consistency}
Figure~\ref{fig:by-scene} shows that the efficiency gain holds across all five scenes for both views and tokens, though its magnitude tracks scene structure. The Theater, with a clean zone layout, yields the largest token savings (80.9\%), while the outdoor drone scene---fewer views and a flatter tree---yields the smallest (50.4\%). No scene regresses, indicating the benefit is a property of the hierarchy rather than of one favorable environment.

\subsection{Legacy demo scene}
On an earlier single-scene Conference Hall demo (19 views, a 15-node tree) with 12 queries, graph traversal reduces input tokens by 4.1$\times$ and views checked by 4.8$\times$, with an estimated 4.0$\times$ latency speedup under a documented LLM timing model. We keep this result separate from the five-scene averages because it uses an estimated timing model rather than the stub measurements above.

\subsection{Case studies and failure analysis}
To probe behavior beyond aggregate numbers, we run five curated room-scoped queries on the demo scene and classify the returned view by room (Figure~\ref{fig:failure}). These cases surface three qualitatively different regimes.

\paragraph{Efficiency at equal correctness.}
On the three ``screen'' queries, graph traversal and flat search return the \emph{same} correct view, but graph reaches it after checking 2 views ($\approx$2.9k tokens) versus flat's full 19-view scan ($\approx$23k tokens)---an order-of-magnitude cost reduction with no loss of correctness. This is the intended operating regime: when a query localizes to one zone, the tree confirms early.

\paragraph{Failure mode 1: uneven pruning.}
For ``find the projector in the ballroom,'' the target view sits in a large, densely populated zone. Graph traversal still reaches the correct room, but only after checking 16 of 19 views, so its cost approaches the flat baseline. Hierarchy provides little benefit when the answer is spread across a broad zone rather than isolated in a narrow branch.

\paragraph{Failure mode 2: shared retrieval miss.}
For ``where is the exit sign in the lobby,'' both methods miss: the current lexical stub index does not surface a matching view. Graph traversal nevertheless fails \emph{cheaply}, checking 3 views before returning empty, whereas flat search still pays for a full scan. This isolates a limitation of the retrieval backend (not the hierarchy) and shows that pruning also bounds the cost of failures.

We note that, on the current scene state, flat search does \emph{not} exhibit wrong-room errors on these queries; both methods agree on the room when they succeed. The value of hierarchy here is cost control at matched quality, not higher accuracy.

\subsection{Baselines and scope}
ConceptGraphs and LangSplat smoke tests confirm adapter feasibility but do not provide five-scene accuracy or efficiency comparisons, so we make no head-to-head claim. Live and cached-live provider evaluation, and ScanNet-scale benchmarking, are out of scope for this study.

\section{Discussion}
Three patterns emerge. First, the savings are driven by \emph{early pruning}: whenever a query can be localized to a zone from its summary, the tree discards the majority of views before any leaf check, which is why negatives and simple objects gain most. Second, the small hit@3 gap in favor of flat search reflects a genuine trade-off---exhaustive search never prunes a correct-but-distant candidate, while the tree occasionally does. In cost terms, however, the graph reaches comparable hit@1 while reading roughly one third of the tokens. Third, because both methods share inputs, these effects are attributable to structure alone, which is the property we set out to isolate. Together this suggests hierarchy is most valuable as a \emph{cost-control} mechanism for environment queries, with quality parity rather than a quality win.

\section{Limitations}
\begin{itemize}
    \item \textbf{Manual reference labels:} expected objects and views are verified from annotations, not independent annotators, so absolute hit@k should be read as relative graph-vs-flat evidence.
    \item \textbf{Stub evaluation mode:} five-scene runs use lexical stub matching, not live VLM calls; live behavior may differ.
    \item \textbf{No metric 3D localization:} independent 3D boxes are unavailable, so 3D IoU is not reported.
    \item \textbf{Uneven benefit:} multi-hop queries retain high view counts; savings depend on query type and tree shape.
    \item \textbf{Baselines:} external methods are literature context plus minimal smokes, not same-input comparisons.
\end{itemize}

\section{Conclusion}
SemanticSplat shows that hierarchical graph pruning substantially reduces the cost of semantic search over captured 3DGS scenes while preserving retrieval quality, under a controlled protocol where graph and flat methods consume identical semantic items. Across five scenes, six query types, and 150 queries, graph traversal cuts views checked by 71.4\% and tokens by 65.1\% at comparable hit@1, with the largest gains on queries that localize to a single zone. Future work includes live VLM evaluation, richer zone--region--object graphs, independent ground truth, and fair same-input comparison against external scene-graph systems.
